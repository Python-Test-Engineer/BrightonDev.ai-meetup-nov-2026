How a coding agent actually works

A complete coding agent in 948 lines of plain Node: one HTTP request, six tools, a loop with four bounds, and a folder it cannot escape. Read it top to bottom, or jump to the part you doubt.

01What an agent actually is

Strip the branding off a coding agent and three things remain: a model that can only produce text, a set of tools that can actually do something, and a loop that hands the model's own text back to it as an observation. Everything else — retries, memory, sub-agents, skills, permissions, project rules — is a layer laid on top of those three.

mini-coding-js is those three things and nothing else: 948 lines in src/, one dependency (chalk, for colour), no SDK, no framework. The model is reached with a single fetch. This page walks the whole program, in the order you would read it.

The whole idea, in six lines

That is not a simplification of an agent — it is the agent. A chatbot is the same program with the loop deleted: one model call, one answer, no way to look at the world and react to what it saw. The rest of this page is the detail behind each line: what the model request contains, what a tool call really is, and what stops the loop from running forever.

What it looks like while it runs

Read those four lines as a sentence: the model thought, it acted, the world answered, and the loop went round again with that answer in hand. Every coding agent you have used prints a variation of this. Nothing in the middle is hidden.

02The shape of the program

Six files, each answering one question an audience usually asks. They import in one direction only, so there is no cycle to hold in your head.

FileLinesThe question it answers
src/agent.js300Where is the loop? Also the CLI, the input field and the scripted demo.
src/tools.js318What can the model do, and what happens when it asks?
src/config.js128Which key, which model, which limits — and where each value came from.
src/workspace.js85How is a path stopped from leaving the sandbox?
src/llm.js66What exactly goes over the wire?
src/ui.js51Where is the colour? (Nowhere else.)

There is no plugin registry, no abstract base class, no event bus. TOOL_SCHEMAS is an array literal and HANDLERS is an object literal whose keys happen to be the tool names; the dispatcher is thirty lines. To add a seventh tool you would edit two places and be done.

Read it in this order. agent.js first, out loud, skipping the banner code at the bottom. Then tools.js top to bottom, because the schema descriptions are the only prompt engineering in the project. Everything else is plumbing you can skim on the projector.

03The loop

runTask is the whole agent. It takes a task, builds the first two messages, and then runs the same seven beats until the model stops asking for tools or the step budget runs out. Here it is with the logging lines removed (agent.js:41–105):

The seven beats

#What happensWhere
1A step heading is printed and a 5-second heartbeat is armed, so a slow provider never looks like a frozen program.agent.js:52–57
2One model call: the entire message array plus the six tool schemas. Nothing else is sent.agent.js:59
3A truncated reply (finish_reason: "length" with no tool calls) is never dispatched as half a call; the model is told to continue smaller.agent.js:71
4The assistant message is pushed back into history, stripped to the fields an agent needs.agent.js:78
5No tool calls means the model is finished: print the answer, return ok: true.agent.js:83
6Each tool call is dispatched, its result logged, and the string appended as a role: "tool" message.agent.js:90–100
7Loop. The next request now holds the model's own intention and the world's answer to it.agent.js:52
The loop is the agent. Delete the for and you have a chatbot with tools it will never call. Keep it, and the model can look, act, observe and try again — which is the entire difference between "answers questions about your code" and "changes your code".

04The model call

There is no SDK in this project, on purpose. A tool-calling request to an OpenAI-compatible endpoint is a POST with three interesting fields: model, messages and tools. The whole client is 66 lines (src/llm.js).

Two details are worth a minute on stage.

  • AbortSignal.timeout is the entire liveness story at the transport layer. A socket that never answers becomes an error after 90 seconds instead of a hung agent. The heartbeat in agent.js covers the same worry at the human layer: … still waiting for the model (25s).
  • Failures here throw; failures in a tool do not. A bad key, a 402, a dropped connection is not something the model can fix, so it stops the run with exit code 1. A failed edit is something the model can fix, so it comes back as text.

Sanitising the assistant message

Providers return extra fields on the assistant message — reasoning, reasoning_content, refusal blocks, annotations. Echoing them back re-sends the model's private scratchpad on every subsequent step: tokens you pay for, and a context that fills with stale thinking.

max_tokens: 2048 is deliberately small: it keeps each step cheap and keeps whole files out of a single reply. The cost is that long answers get cut off — which is exactly what the truncation guard in the loop is for.

05Messages are the memory

The messages array is the agent's entire working state. There is no database, no scratchpad file, no summary of what happened earlier. Delete the array and the agent has no idea it ever did anything.

RoleWho writes itWhat it carries
systemyouThe job description: five numbered rules about looking before writing, copying snippets exactly, running what it wrote, and stopping when done.
useryouThe task — one plain sentence, or one corrective nudge (the truncation message is also a user turn).
assistantthe modelcontent (its thinking, printed as think:) and possibly tool_calls — its intentions.
toolthe harnessOne string per call, tagged with the tool_call_id it answers. The only way the model learns what happened.

That is why the push happens inside the same for that ran the tool — even when the tool returned an ERROR string, because an error is still an answer.

Prompt design lives in three places, all of them ordinary code. The SYSTEM_PROMPT in agent.js (how to work), the schema descriptions in tools.js (what each tool is for), and the error strings the handlers return (how to recover). There is no separate "prompt file" to load at runtime.

06The six tools

A tool is two things that must agree: a JSON schema the model reads, and a JavaScript function that runs when the model names it. The model never touches the filesystem — it emits JSON naming a tool, and the harness executes it.

ToolWhat it does
list_filesRecursive listing, depth 3 by default (max 6), skipping node_modules, .git, .venv, __pycache__. Capped at 200 entries.
read_fileLine-numbered, paged via offset/limit, and says how many lines remain.
create_fileFails if the file already exists — forces the model to edit rather than clobber.
write_fileCreate or completely overwrite; parent folders are made for you.
edit_fileExact-snippet replace. Zero matches is an error; more than one is an error unless replace_all.
run_commandShell in the workspace root, 30 s timeout, returns exit code plus stdout and stderr.

The schema is the prompt

When the model chooses a tool it reads nothing but these descriptions. That makes them the highest-leverage text in the codebase — and the place to fix a model that keeps picking the wrong tool.

Note what the description does: it states the precondition ("fails if the file already exists") and names the alternative. A model told that reaches for edit_file instead of blindly overwriting. additionalProperties: false matters too — it discourages invented arguments, and the dispatcher rejects wrong types anyway.

The dispatcher

Three rules are visible in those lines and they hold for every tool:

  • It returns a string, always. Success, denial, unexpected exception — everything is text the model will read on the next step. A thrown error would escape the loop and end the run; a returned ERROR: … is an observation the model can act on.
  • Arguments are parsed and typed before dispatch. validate() catches the common failure of a model sending "limit": "20" instead of 20, and answers with ERROR: "limit" must be a integer, got string rather than a confusing crash two frames down.
  • Unknown names are survivable. A hallucinated tool name gets a helpful list back and the loop keeps going. Models do this; the harness is expected to be patient about it.
Exit codes close the loop. run_command reports exit code 0 versus exit code 1 as text, which is how the agent knows whether the code it just wrote actually works. A tool that returned only stdout would let a failing script look like a success.

07edit_file, the interesting one

Five of the six tools are obvious. edit_file is the one that teaches something, because it is where an agent's output is most likely to be subtly wrong, and where good harness design turns that into a recoverable moment instead of a corrupted file.

Every failure mode, and why it is a message

SituationWhat comes backWhy that is right
Snippet is not in the fileERROR: old_string not found … copy the snippet exactly, including whitespace.The model hallucinated whitespace. The message says what to do next, so the following step usually fixes it.
Snippet appears 4 timesERROR: old_string appears 4 times … pass replace_all: trueSilent first-match replacement would edit the wrong function. Ambiguity must be an error, not a guess.
Snippet is ""ERROR: old_string must not be emptyAn empty search string would otherwise "match" everywhere.
Replacement contains $1replaced literallyString.replace interprets $1 when the second argument is a string; the callback form removes the footgun.
File does not existERROR: no such file: …Points at the missing step without being asked.

This is the clearest demonstration of the fourth principle on the page: an error is an observation, not a crash. The failure costs one step and arrives as a sentence the model can read, which is why a live demo should include a forced failure — ask the agent to edit something in a way that cannot match, and watch the loop absorb it.

08The sandbox

Every file tool resolves its path through one function, Workspace.resolve(). If a path cannot be proven to be inside workspace/, the tool refuses before a single byte is written.

The interesting part is that a plain path.resolve plus startsWith check is not enough on Windows, because several ordinary-looking strings resolve inside the workspace root:

The model asks forWhat happensWhy a naive check fails
C:\Windows\x.txtrefused: absolute or drive-relative pathThe regex fires before path.resolve can reinterpret C:.
\\server\share\xrefused: UNC pathUNC paths bypass drive-rooted containment entirely.
~/notes.txtrefused: home/environment path~ expands to the home directory after resolution.
%USERPROFILE%\xrefused: home/environment pathEnvironment expansion is not traversal, so .. checks miss it.
Desktop\notes.txtrefused: looks like a home/system folderWith the cwd inside a user profile this resolves happily to a real Desktop.
../../secrets.txtrefused: path escapes the workspaceCaught late, by the containment check.
link-to-home\xrefused: path escapes the workspaceA junction would pass a string check; realResolve follows it first.

realResolve exists for the last row: it walks up to the deepest ancestor that exists, resolves that with fs.realpathSync, then re-appends the not-yet-created tail. A junction pointing out of the sandbox is compared by its real target, not by its name. The tests cover every shape in the table.

The honest limit. run_command is a real shell. It starts in workspace/, but nothing stops a command from walking out of that folder — the directory is not an operating-system sandbox. Isolation is a container's job. Saying this out loud beats implying the demo is safe by construction.

09Human in the loop

Everything so far lets a model act. This chapter is the part that lets you decide how much. There is one setting, CMD_POLICY, and it governs the only tool that can do damage a file check cannot contain: run_command.

CMD_POLICYBehaviourWhen you would use it
ask defaultEvery command stops and waits for a y/N at the terminal. n returns DENIED: the user did not approve this command. to the model.Live demos, and any run you are watching. The pause is the point.
allowCommands run without asking. Set by --yes / --allow-commands, or by CMD_POLICY=allow.The scripted demo, CI, or a task you already trust.
denyNo command runs at all; the model gets a denial and can still edit files.Read-mostly tasks, or a run with no terminal attached.

The approval sits in the handler, not in the loop, so a denied command behaves like any other observation:

What is refused no matter what the policy says

Eight patterns are checked before the policy is consulted, so allow cannot unblock them. They are not a security boundary — they are a seatbelt against a model that has read too many bad shell examples.

PatternRefused because
rm -rf /, rm -rf ~recursive delete of a root path
del /s, del /qrecursive or quiet Windows delete
format, diskpartdisk formatting
shutdown, rebootmachine power control
git push --force, git push -fforce push
curl … | sh, wget … | bashpiping the internet into a shell
:(){ :|:& };:fork bomb
> /dev/sdaraw disk write
The non-TTY rule. With no terminal attached (piped input, CI, a scheduled run) the ask policy degrades to deny. An unanswerable prompt must never become an approval — the confirm function defaults to async () => 'deny' for exactly this reason.

10The console palette

One file knows about colour. Every line the agent prints is a named helper in src/ui.js, so the loop itself contains no escape codes and the whole palette can be swapped in one place.

Two design decisions make this more than cosmetics.

  • chalk styles the exact string you hand it. There is no markup to parse, so text from the model or a tool prints verbatim: a file containing <red> shows up as <red>, and Windows backslashes and JSON survive intact. A console library that interprets inline tags would quietly corrupt the very output the audience is reading.
  • Every helper returns a string and nothing writes to stdout. That is why runTask can take an injected log, and why the loop can be tested without capturing a terminal.

The colour of a result is derived, not reported by the tool: isFailure looks for ERROR, DENIED or an exit code other than 0 in the first line.

That small regex is the visual contract of the whole demo: anything red means the model has a problem to solve on the next step. chalk decides whether to colour at all — NO_COLOR, FORCE_COLOR and "output is a pipe" are all honoured — so redirecting a run to a file gives clean text.

11Configuration and precedence

Three sources compete for the key and the model name, and the winner is printed on every start with its provenance. The ladder is deliberately not the usual one:

.env beating the shell is a choice, not an accident: a stale OPENROUTER_API_KEY in ~/.bashrc would otherwise silently outrank the key you just wrote, and you would spend an afternoon on a 401. Variables .env does not mention still come from the environment.

Finding the file is a walk upwards, so the single .env at the repository root works for a package one level down:

The knobs

VariableDefaultWhat it does
OPENROUTER_API_KEY / OPENROUTER_KEYrequiredThe key. Only ever printed as sk-or...aaa5 (73 chars).
OPENROUTER_MODEL / MODELdeepseek/deepseek-v4.1-flash-1017Which model. MODEL= is an alias for older .env files in this repo.
CMD_POLICYaskallow / ask / deny.

Two small kindnesses

  • Fingerprinting instead of printing. fingerprint() returns sk-or...aaa5 (73 chars) — enough to tell two keys apart on stage, useless in a screenshot.
  • Normalising bare model names. OpenRouter needs vendor/model, and a .env carried over from another project usually holds gpt-5. A prefix table maps deepseek*, claude*, gpt*, gemini*, grok*, llama*, qwen*, mistral* to a vendor, and the banner says when it guessed.

12Bounded autonomy

An agent that can loop is an agent that can loop forever. Four bounds cap it, and each one has a visible consequence rather than a silent stall.

BoundWhat it preventsWhat you see
maxSteps (12)A model that keeps reading files and never concludes.stopped: hit the 12-step limit, exit code 3.
finish_reason: length guardHalf a tool call, dispatched as JSON that will not parse.reply was truncated - asking the model to continue smaller.
REQUEST_TIMEOUT_MS (90 s)A socket that never answers.request failed: request timed out after 90s, exit code 1.
run_command timeout (30 s)A command that hangs the whole run.[tool] command timed out after 30s in the stderr block.

The heartbeat

Between them, those bounds would still leave a 90-second silence, which on a projector looks identical to a crash. So a timer prints something every five seconds while the request is in flight:

It is armed just before the call and stopped just after, including on the failure path. unref() matters: a timer that holds the event loop open would turn a clean exit into a program that hangs for five more seconds.

Exit codes

CodeMeaning
0The model stopped calling tools and gave an answer.
1The request failed — bad key, no credits, timeout, non-JSON.
2No task: nothing typed at the prompt, the field closed, or stdin is not a terminal.
3Stopped at the step limit.
Why the truncation guard is the interesting one. A cut-off reply often ends mid-JSON: {"path": "hello.js", "cont. Dispatching that would produce ERROR: could not parse arguments for a tool call the model never finished, and the model would spend a step apologising for a bug it did not have. Refusing to dispatch it is the difference between a harness that respects the model and one that argues with it.

What to point at

  • Step 1 failed, and the run carried on. demo/hello.js was left over from an earlier run, so create_file refused to clobber it.   • Step 5 has no tool → line. The model said it was done, the loop took the calls.length === 0 branch, printed the final answer and returned. That branch is the only way out other than hitting the limit.
  • The banner was printed before the first step. Model, key fingerprint, which .env won, the policy, the timeout and the tool list — the whole configuration as one reproducible header, which is what you want when a demo goes wrong on stage.

14Run it yourself

Node 20+ and one npm install. The .env at the repository root is found automatically, so nothing has to be copied for a live run.

The five-minute talk script is in the README: run --demo and narrate think → tool → result → think; delete workspace/demo/hello.js and run it live with --yes; then ask for an edit that cannot match, so the audience sees the error come back as a tool result and the model repair it on the next iteration.

A demo that fails on purpose is worth two that succeed. The happy path shows what an agent does. The failure shows why the loop matters: it is the only structure that lets a model recover from being wrong, which is the thing no single completion can do.

15What it deliberately does not do

The limits are worth stating as plainly as the features, because each one is where a production agent grows a layer this demo does not have.

  • The shell is not sandboxed. run_command starts in workspace/ and can walk out of it. File tools are contained; commands are trusted as far as your policy allows.
  • No context management. messages grows with every step and nothing trims it. Long runs will eventually exceed the window — which is where summarising, retrieval and compaction start to matter.
  • No streaming. Each step waits for a complete reply, so the heartbeat exists to make the wait legible. Streaming would delete that problem and add a parser.
  • No sub-agents, no retries, no skills, no memory. Every one of those is a layer on top of this loop, not a replacement for it, and all of them assume the loop already works.
  • One tool at a time in spirit. Multiple calls in a single reply are dispatched in order, but the system prompt asks for one per step because interleaved edits are much harder to audit live.
