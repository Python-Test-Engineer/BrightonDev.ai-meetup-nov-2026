Sandbox · the ladder

From a path check to a container

The explainer's chapter 08 admitted the limit: file tools are contained, a shell is not. This is every option for closing that gap, cheapest first — code, then the operating system, then Docker, then the tiers you only need once someone else's code runs on your machine.

7 tiers tier 1 = 85 lines tier 4 = docker run 1 interface 9 red-team checks

01What a sandbox is for

Chapter 08 of the explainer ended on a warning: the file tools are contained, but run_command is a real shell and nothing stops it walking out of workspace/. That is the honest answer for a laptop demo, and it is also the point where the interesting engineering starts.

This page is the build-up in the order you would actually do it: containment in code first, because it is free and it teaches you what the threat is; then process hardening; then the operating system; then Docker, which is the step most teams take next; then the things that exist once a container is not enough. Each tier is described by what it stops, what it costs, and what it does not stop.

A container is not a magic word. It is one rung on a ladder, and the rungs below it are cheap.

QuestionHonest answer
What is being sandboxed?Two different things: files the agent writes, and commands it runs. The second is the hard one.
Against whom?A model that is wrong, not an attacker with shell access. Those are different threat models and they want different tiers.
What does “enough” mean?Enough that a mistake costs a file, not your home directory, your API key, or the machine.
Threat model first, mechanism second. A watched live demo has a human in the loop, which is already a control. An unattended loop at 2 a.m. has none, and that is the run that justifies a container.

02The ladder

Seven rungs, cheapest first. Each one is a superset of the one above it, and each one buys a specific property rather than “security” in general.

The useful rule: climb only as far as the unattended case requires. Tiers 1–2 are worth having even at tier 4, because they fail with a readable error instead of a container startup cost — and they are what the tests can exercise offline.

03Tier 0 — the prompt

Tier 0 is what most agent demos ship: a system prompt that says work inside the sandboxed folder, plus an approval prompt on commands. It is worth naming as a tier rather than skipping, because it is not nothing — and because its failure mode is instructive. A model that has read a thousand shell tutorials will eventually cd .., not out of malice but because it is trying to be helpful.

On the day the model is helpful in the wrong direction, tier 0 turns a demo into an incident. The rest of this page is the cheap insurance.

Language matters here. Calling the folder a “sandbox” when only the prompt enforces it is how a demo becomes a cautionary tale. Either the mechanism is there or the claim is not.

04Tier 1 — containment in code

This is the rung the repo is already on, and the first one worth writing because it costs nothing and its tests never touch the network. Every file tool funnels through one function, so there is exactly one place to be right.

Two design choices are worth copying whatever tier you land on. First, the check throws a typed PathError that the dispatcher turns into an ERROR: string, so a refusal is an observation the model can read rather than a crash. Second, it refuses before resolving, so the error message describes the request instead of a half-computed path.

What tier 1 buys: a model that hallucinates ../../../.env gets a sentence back and tries again. What it does not buy: anything about run_command, which has no path to check because a shell is not a path.

05Tier 2 — process hardening

The next rung is still ordinary code, and it is where most of the real-world value is. Four things, none of them exotic: a deny-list, a timeout, an output cap, and an environment scrub.

A deny-list is a seatbelt, not a boundary: it catches the eight ways a model ruins a demo, and it catches nothing that was written to get past it. That is fine at this rung, as long as nobody calls it isolation.

The three bounds around a spawned process

The environment is the leak nobody notices. A child process inherits process.env, which holds OPENROUTER_API_KEY. One echo $OPENROUTER_API_KEY puts the key into messages, which goes back to the provider and into your logs. safeEnv() should hand the child a short allow-list — PATH, HOME, TMPDIR, nothing else.

killTree matters more than it looks: a 30-second timeout that kills only the shell leaves node or npm running, and a demo with three orphans on port 5000 is a demo that “mysteriously” stopped working.

06Why hardening is not isolation

Everything in tiers 1–2 is advice the process gives itself. The process can also ignore it, because the model does not run in the harness — it emits a string, and the harness hands that string to a shell that has all of the harness's privileges.

So why bother? Because these two rungs make the common case fail loudly and cheaply, and they keep working after you add a container. A refusal that costs one loop step is better than a container start that costs two seconds.

07Tier 3 — operating system

The next rung uses the thing that already exists for this: the operating system. The idea is one sentence — run the command as a different user, in a different namespace, with no network — and the implementations are wildly platform-specific.

Linux: namespaces in one command

Swap bwrap for nsjail when you also want a seccomp filter, a uid map and a per-run network namespace, or for unshare --user --map-root-user --net --mount when you want to write it yourself and debug it. This is the lightest real isolation available on Linux: single-digit milliseconds, no image to build, and the flags are the policy, which makes it auditable.

Windows: no equivalent, and that is the finding

Pragmatic conclusion: on Windows, tier 3 is either “add bounds and accept the gap” or “go straight to Docker”. Nobody writes an AppContainer wrapper for a meetup demo, and the people who do are writing it for a product.

08Tier 4 — Docker

This is the rung most teams land on, and the one this page spends its time on, because it is the first that gives you a disposable filesystem and a network namespace and works the same on Windows, macOS and Linux — once Docker Desktop is installed.

The whole design fits in one docker run. The flags matter more than the image:

FlagWhat it prevents
--network noneExfiltration, npm install at run time, and a model that decides to fetch a package it half-remembers.
--read-only + --tmpfs /tmpWrites anywhere except the mount and a 64 MB scratch dir. Deleting the container deletes them.
--memory, --memory-swapA runaway allocation that takes the laptop with it.
--pids-limitFork bombs, and npm's habit of spawning a process tree.
--cpus 1A hot loop that makes the demo machine unusable.
--cap-drop ALLThe handful of capabilities root-in-container gets by default.
--security-opt no-new-privilegesRegaining privilege through a setuid binary.
--user 65534:65534Files in the mount being written as your user — nobody has to be given permission deliberately.
--rm --initLeftover containers, and zombie children holding the image lock.
The one flag you must never add. Do not mount /var/run/docker.sock into the sandbox. It is not a file, it is root on the host: anything with the socket can start a privileged container and mount /.

09What Docker does not give you

A container is a process with a convincing costume: the same kernel, a different view of it. That view is strong enough for the threat model in chapter 01 and weak enough that it must be described accurately.

ClaimReality
“The container cannot see my files”True for everything not mounted. The bind mount is deliberate and is the escape hatch you built.
“The container cannot escape”It shares the host kernel. A kernel privilege-escalation bug is a container escape; that is why tier 5 exists.
“It runs as nobody so it cannot hurt anything”True until something in the mount is owned by nobody, or a setuid binary creeps into the image.
“The code inside is safe to run”The image is code you pulled from a registry. Pin by digest and rebuild it yourself, or the sandbox's supply chain is the model's supply chain.
“Docker Desktop on Windows is a Linux host”It is a VM. That is better for you — the host filesystem is not the container's kernel neighbour — but the mount is still a real host folder, and it is slow.
“A symlink written in the mount is harmless”The container can create workspace/x -> C:/Users/you/.ssh. Host-side file tools must still call resolve(), which realpaths the link and refuses it. Container isolation does not replace the check; it protects the shell.
Keep tier 1 running underneath tier 4. The container guards the shell; Workspace.resolve() guards the file tools, including anything the container left behind in the shared folder. They cover different holes.

The costs nobody mentions in the slide

  • Image pull is the real start time. A warm local image starts in a fraction of a second; the first run on a fresh laptop pulls hundreds of megabytes over the meetup wifi, in front of the room.
  • Docker Desktop is another failure surface. A demo that now has two ways to fail (the model, and the daemon) needs a fallback: --sandbox local should still work.
  • Bind-mount permissions on Windows map differently through the VM, so files land as a uid the host does not have. chmod inside is cosmetic; plan for it or the npm test inside the container fails for a reason unrelated to the agent.
  • Networking is off, so nothing installs. If the task needs a dependency, bake it into the image or mount a node_modules — the model cannot invent one at run time, which is a feature you should say out loud.
  • Startup latency lands inside the loop. One container per command is correct and slow (~0.5 s each). One long-lived container with docker exec is fast, and now the command has state — a shell that remembers cd, and files that persist between steps. That is usually what you want; it is a different design, and it needs a stop().

11Tier 6 — someone else's machine

Two ways to not run the sandbox yourself. They look similar and solve different problems.

Hosted sandboxes: an API call per run

GainGive up
Isolation is their problem, and they take it more seriously than you willEvery command is a network round trip; the demo now needs wifi
Per-run VM or microVM, so state cannot leak between usersYour workspace lives on someone else's disk, and so does the code
Horizontal scale: one sandbox per task, ten at onceLatency floor of a few hundred ms per call, plus a vendor SDK in the tool handler
No Docker Desktop on the demo laptopAn account, a key, and a quota — three new ways for the talk to fail
The honest fit: tier 6 is right for a product that runs untrusted code for strangers. For one laptop and one audience it is more moving parts than the risk justifies — but it is the right answer to “how would you ship this?” and worth one slide.

WASM: a sandbox for expressions, not for programs

If the untrusted thing is a computation rather than a coding agent, a WebAssembly runtime is the cheapest real boundary there is: no syscalls to intercept, an in-memory filesystem, no network, and microsecond start-up. QuickJS or Pyodide in a Node worker gets you a scripting sandbox in a few dozen lines.

It is not a coding sandbox. There is no npm, no native binary, no long-running server, no git, and no spawn — which is exactly the list a coding agent needs. File it under “the other tool you might reach for”, not under “the answer”.

12Wiring it into the agent

Every tier above changes what happens inside run_command and almost nothing else. That is the argument for defining the seam early: one module, one contract, three implementations, chosen by config.

Three things to keep in mind when you do this refactor.

  • Keep HARD_DENY and CMD_POLICY outside the sandbox. They are policy about the model, not capability of the runtime. A container does not make git push --force acceptable.
  • Let the file tools stay host-side at tier 4 — the mount makes it work, and resolve() keeps working. Only at tier 6 do reads and writes become RPC, and that is when the tool handlers genuinely change shape.
  • Make the mode a startup banner line. sandbox: docker (network none, 512 MB) printed once tells the audience, and tells you in a bug report, which tier is actually running.
Name the degradation explicitly. If Docker is missing, do not silently fall back to local. Print sandbox: local (no isolation for commands) and carry on — a visible downgrade is safe, a silent one is how the wrong thing ships.

14Which rung, when

The short version, for the demo and for the talk.

SituationDo thisWhy
The meetup demo, you at the keyboardtiers 1–2, CMD_POLICY=askThe human is the control, and the loop is the thing you are showing.
Unattended run on your own machinetier 4, --yes, --network noneThe container bounds the worst case; the deny-list still stops the obvious.
CI, or a second contributortier 4, one container per taskReproducible: the image is the environment, and nothing secret is mounted.
Running other people's codetier 5 or 6Kernel boundary or their machine. Container isolation is not enough for strangers.

And the two sentences worth saying out loud in the room, because they are the whole talk:

1. The sandbox is not the security model — the interface is. Once run_command goes through one function, isolation becomes a flag, and you can climb the ladder without rewriting the agent.

2. Every tier below the one you need is a bug report waiting to happen; every tier above it is a demo that will not start. Tier 4 is the default because it is the cheapest rung that survives being left alone.

Then demo the failure, not the success. Ask the agent to cat .env, let the refusal come back as a tool result, and watch it try another way — that is the loop doing its job, and the sandbox doing its.
